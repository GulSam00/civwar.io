# WebSocket 프로토콜 QA — 경계면 정합성 검증 절차

멀티플레이어 게임에서 가장 흔한 버그는 서버와 클라이언트가 각각 "정상적으로 동작"하지만 서로 주고받는 메시지의 실제 shape이 어긋나는 경우다. 정적 타입 검사(TypeScript 컴파일)는 이 버그를 못 잡는다 — 런타임 JSON 페이로드는 타입 시스템 밖에 있기 때문이다. 반드시 **문서와 코드 양쪽을 동시에 읽고 대조**해야 발견할 수 있다.

## 검증 절차

### 1단계: 프로토콜 문서 ↔ 서버 실제 전송 대조

1. `_workspace/02_backend_protocol.md`에서 `Server → Client` 섹션의 모든 메시지 타입과 필드 목록을 추출한다
2. 서버 코드에서 `ws.send(`, `broadcast(`, `.emit(` 등 실제 전송 지점을 모두 검색한다 (Grep으로 패턴 검색)
3. 각 전송 지점의 실제 payload 구조를 문서의 정의와 비교한다:
   - 문서에 없는 필드를 서버가 보내고 있는가 (문서 누락)
   - 문서에 있는 필드를 서버가 안 보내는가 (구현 누락, 또는 이름이 다름 — camelCase/snake_case 혼용 여부 확인)
   - 문서에 정의된 메시지 타입인데 코드 어디에도 전송하는 곳이 없는가 (죽은 스펙)

### 2단계: 프로토콜 문서 ↔ 클라이언트 실제 파싱 대조

1. `_workspace/02_backend_protocol.md`에서 `Client → Server` 섹션과 클라이언트가 수신 처리하는 `Server → Client` 메시지 목록을 추출한다
2. 클라이언트 코드에서 메시지 핸들러(`onmessage`, `switch (msg.type)` 분기 등)를 찾는다
3. 각 분기가 실제로 접근하는 필드가 문서에 정의된 필드와 일치하는지 비교한다 — 특히 다음을 주의한다:
   - 옵셔널 필드를 클라이언트가 무조건 있다고 가정하고 접근하는가 (`msg.tiles[0].owner.name`처럼 null 가능성을 무시한 체이닝)
   - 배열/객체 래핑 여부 (`{ tiles: [...] }` vs 클라이언트가 배열 자체를 기대)
   - 문서에 정의된 클라이언트 발신 메시지 중 실제로 어디서도 보내지 않는 것이 있는가 (미구현 기능)

### 3단계: 게임 규칙(GDD) ↔ 서버 로직 대조

1. `_workspace/01_game-designer_gdd.md`의 성장 공식, 전투 해석 규칙, 승리조건을 추출한다
2. 서버의 tick 처리 로직(자원 생산 계산, 전투 판정, 승리조건 체크 함수)을 찾는다
3. 각 공식/규칙이 코드에 정확히 반영됐는지 대조한다. 특히:
   - GDD가 tick 단위 공식을 명시했는데 서버 tick 간격과 계산 주기가 다른가
   - 동시 다발 액션 처리 규칙이 GDD에 있는데 코드가 임의 순서(예: 배열 순서)로 처리하고 있지 않은가

### 4단계: 좌표/단위계 일치 확인

서버의 타일 인덱싱 방식(예: `row*width+col`)과 클라이언트의 렌더링/클릭 변환 로직이 같은 좌표계를 쓰는지 확인한다. 다르면 "서버는 정상, 클라이언트도 정상으로 보이는데 클릭한 곳과 다른 타일이 선택되는" 형태의 버그가 생긴다.

## 체크리스트

```markdown
### civwar.io 통합 정합성 검증

#### 프로토콜 문서 ↔ 서버
- [ ] 문서의 모든 Server→Client 메시지가 실제 코드에서 전송됨
- [ ] 서버가 실제로 보내는 모든 메시지가 문서에 정의됨 (문서에 없는 필드 없음)
- [ ] 필드명 표기(camelCase 등)가 문서와 코드에서 일관됨

#### 프로토콜 문서 ↔ 클라이언트
- [ ] 클라이언트가 파싱하는 모든 필드가 문서에 정의되어 있고 실제로 서버가 채움
- [ ] 옵셔널/nullable 필드에 대한 방어 코드가 있음 (무조건 존재 가정 없음)
- [ ] 문서의 Client→Server 메시지가 실제로 UI에서 트리거됨 (미구현 없음)

#### GDD ↔ 서버 로직
- [ ] 성장/전투 공식이 서버 tick 로직과 일치
- [ ] tick 간격이 GDD의 시간 단위 가정과 일치
- [ ] 동시 액션 처리 규칙이 GDD와 일치
- [ ] 승리조건 판정이 GDD와 일치, 제한시간 도달 시 처리도 구현됨

#### 좌표/단위계
- [ ] 서버 타일 인덱싱과 클라이언트 렌더링/클릭 변환이 같은 좌표계 사용

#### 엣지 케이스
- [ ] 재접속 시 상태 복구 동작
- [ ] 마지막 1명 남았을 때 게임 종료 처리
- [ ] 최대 인원 초과 시 참가 거부
```

## 보고 형식

발견한 각 이슈는 다음 형식으로 기록한다 — "버그가 있다"로 끝내지 않고 재현 가능한 근거를 남긴다:

```markdown
### [실패] STATE_UPDATE의 troops 필드 불일치
- 문서(`_workspace/02_backend_protocol.md` L42): `"troops": number`
- 서버 코드(`server/src/room.ts` L88): `troopCount`로 전송
- 클라이언트 코드(`client/src/hooks/useGameSocket.ts` L23): `msg.tiles[i].troops` 접근 → 항상 undefined
- 영향: 모든 영토의 병력 수가 화면에 표시되지 않음
- 수정 방법: 서버 필드명을 `troops`로 통일하거나 문서를 `troopCount`로 갱신 (둘 중 하나로 통일, 양쪽 다 수정하지 않으면 재발)
```

미검증 항목(해당 모듈 미완성 등)은 "미검증"으로 명확히 구분하고, 통과 항목도 근거(어느 파일 어느 줄을 대조했는지)를 남겨 재검증 시 중복 작업을 줄인다.
