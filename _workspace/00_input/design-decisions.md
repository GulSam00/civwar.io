# civwar.io — 사용자 확정 설계 결정 (2026-08-04)

GDD 작성 전, 사용자와의 체크리스트 Q&A로 확정한 결정 사항. game-designer는 이 결정을 **전제로** GDD를 작성한다. 이 결정들을 임의로 뒤집지 않는다.

## 프로젝트 목표
- 온라인에서 사람들과 **25~32분(표준 30분) 안에** 승부를 (2026-10-08 변경, 구 30~60분) 내는 실시간 멀티플레이어 영토 정복 IO 게임
- 장르 레퍼런스: territorial.io, generals.io
- 기술 스택: 클라이언트 React + TypeScript + Vite (Canvas), 서버 Node.js + TypeScript + WebSocket(ws)

## 확정 결정

| 항목 | 결정 | 비고 |
|------|------|------|
| 게임 모드 | **실시간** (턴제 아님) | tick 기반 서버 시뮬레이션 |
| 맵 구조 | **사각 그리드 타일** | 인접 = 상하좌우 4방향, 타일 ID는 `row*width+col` |
| 문명 깊이 | **경량 문명** — 자원 2종 + 간단한 테크 트리 | 세션 중 3~5개 정도 찍는 규모 |
| 자원 | **① 병력 ② 생산력/골드** | 골드는 영토 수에 비례 누적, 테크 구매에 사용 |
| 조작 방식 | **비율 슬라이더 + 자동 전선 확장** | 보유 병력의 X% 설정 후 방향 클릭 → 서버가 매 tick 전선을 자동으로 밀어냄 (territorial.io 방식) |
| 승리조건 | **영토 점유율 임계값 + 제한시간** | 일정 비율 선점 시 즉시 승리, 제한시간 도달 시 최다 점유자 승리 |
| 동시 인원 | **8~12인** | 이 인원 기준으로 맵 크기·성장률을 역산해 세션 25~32분(표준 30분, 2026-10-08 변경)에 수렴시킬 것 |
| 시야 | **전장의 안개 없음 — 전체 공개** | 서버는 모든 플레이어에게 **동일한 스냅샷**을 브로드캐스트 (플레이어별 필터링 불필요) |
| 매치 참가 | **방 코드(비공개) + 공개 로비 둘 다** | 같은 룸 구조를 재사용 |
| AI 봇 | **넣는다** — 단순 확장 AI | 인원 미달 시 빈 자리를 채움. "가장 약한 인접 영토를 공격" 수준으로 충분 |
| 외교 | **간단한 휴전/동맹 제안** | 제안·수락·파기. 동맹 중에는 서로 공격 불가 |
| 탈락 처리 | **관전 모드 + 다른 방 참가 가능** | 부활/재스폰 없음 |
| 테크 트리 축 | **4축 모두**: 군사(공격/방어), 경제(생산력), 영토(점령비용 감소/유지력), 기동(확장·진군 속도) | 각 축을 얕게 (축당 2~3단계 수준) |

## GDD v2 개정 결정 (2026-08-05 추가 — v1.0 검토 후 사용자 확정)

GDD v1.0을 사용자가 검토한 결과 확정된 개정 사항. **v1.0의 4장(전투)은 폐기하고 아래 깃발 모델로 교체한다.**

### A. 전투 모델 전면 교체 — 깃발(Flag) + 병종

v1.0의 "비율 슬라이더 + 자동 전선 확장"을 폐기하고 다음으로 대체한다.

| 결정 | 내용 |
|---|---|
| 명령 단위 | **깃발(Flag)**. 맞닿은 국경 면에 병종과 병력 수를 지정해 깃발을 보낸다 |
| 깃발 이동 | 발령 즉시 도착하지 않고 **전선을 향해 천천히 이동**한다 (이동 시간 = 지연) |
| 깃발 보유 수 | **초기 3개**, 영토 규모 등에 따라 증가 (상한 6~7개 권장) |
| 이동 중 재지정 | **가능**. 단 병종은 발령 시 고정되어 바꿀 수 없다 |
| 병종 | **창병 / 검병 / 기병 3종** |
| 병종 성격 | **역할 분화** (상성 아님) — 창병: 방어력 높고 느림 / 검병: 균형 / 기병: 빠르고 공격 강하나 방어 약함 |
| 병력 보유 | **단일 풀 유지.** 병종은 깃발을 보낼 때 결정되어 풀에서 전환된다 |
| 방어 | **본국 병력 풀이 전 영토를 자동 방어.** 방어용 깃발 배치 없음 |

**상성이 아니라 역할 분화를 택한 이유**: 시야가 전체 공개인데 깃발 이동 지연까지 있으면, 가위바위보 상성은 "먼저 보낸 쪽이 카운터당한다" → 서로 안 보내는 교착을 만든다. 역할이 다르면 선택 기준이 "상대가 뭘 보냈나"가 아니라 "내가 지금 뭘 하려는가"가 되어 이 문제가 사라진다.

**단일 풀을 유지한 이유**: 병종별 풀로 나누면 자원 관리 부담과 UI 복잡도가 IO 게임 수준을 넘고, v1.0의 성장 공식(`√타일`)과 밀도 방어 개념이 전부 무효가 된다. 단일 풀이면 이것들이 살아남는다.

**본국 풀 자동 방어를 택한 이유**: v1.0의 가장 우아한 부분이 "공격에 쓴 병력은 방어력이 아니다"였다. 깃발로 병력을 내보내면 본국 밀도가 떨어진다는 구조를 그대로 유지하면 이 긴장이 보존되고, 방어 조작 부담은 0으로 유지된다.

### B. 지형 5종 + 물

v1.0의 평지/산악 2종을 아래 5종으로 확장한다. **오브젝트(도시·건물·자원 노드)는 도입하지 않는다.** 지형에 "점령비용"과 "골드 산출" 두 축을 독립적으로 부여해 "뺏기 비싼가"와 "가질 가치가 있는가"를 분리하는 것이 목적이다.

| 지형 | 육지 비중(초안) | 점령비용 배율 | 골드 산출 배율 | 역할 |
|---|---|---|---|---|
| 평원 Plain | 38% | 1.00 | 1.0 | 기준 |
| 비옥지 Fertile | 15% | 1.15 | 2.3 | 경제 노른자 = 격전지 |
| 언덕 Hills | 17% | 1.30 | 0.9 | 방어 거점 |
| 사막 Desert | 21% | 0.80 | 0.3 | 넓은 완충지대 |
| 산 Mountain | 9% | 1.85 | 0.3 | 천연 방벽 |
| 물 Water | — | 통행 불가 | — | v1.0과 동일 |

**배치 방식**: 맵 생성 시 이미 계산하는 "물까지의 거리"(v1.0 2.3절 스폰 배치용 BFS)를 재활용한다.
- 거리 1~2 타일 일부 → **비옥지** (강가·해안 평야)
- 거리 큰 내륙 + 노이즈 덩어리 → **사막**
- 별도 노이즈로 **산맥** 생성, 그 둘레 링 → **언덕** (산이 소금후추처럼 흩어지면 벽 역할을 못 한다)
- 나머지 → 평원

부작용으로 스폰(물에서 가장 먼 내륙)은 척박하고 부유한 땅은 해안이 되어, 웅크리기가 손해가 되고 초반 확장 동기가 강해진다 — 의도된 효과다.

**주의**: 위 비중·배율은 오케스트레이터가 잡은 초안이며 검증되지 않았다. 가중평균이 점령비용 1.11 / 골드 0.97로 v1.0(1.04 / 1.00) 대비 확장이 6~9% 느려지므로 상쇄가 필요하다.

### C. 종반 러시

`ENDGAME_RUSH`: 37분 이후 모든 타일 점령비용 **-25%**. v1.0 미결정 사항 7번의 대안을 채택한 것으로, 다수 게임이 42분 타임아웃으로 끝나 마지막 5분이 무의미해지는 문제를 완화한다.

### D. 유지되는 것 (재설계하지 말 것)

- 병력 단일 풀, 타일은 `owner`만 가변
- `√타일` 병력 성장 + 로지스틱 감쇠 + 타일당 상한 12
- 방어 밀도 = 병력 / 타일 수
- 골드 선형 + 테크 4축 3단계 (단, 기동 축은 깃발 모델에 맞춰 재정의 필요)
- 승리조건(점유율 + 임계값 하강 + 하드 타임아웃)과 동맹 규칙 전체
- 시야 전체 공개, 단일 스냅샷 브로드캐스트
- 세션 목표 25~32분, 표준 30분 (2026-10-08 변경, 구 30~60분)

## GDD v2.1 개정 결정 — 기지(Base) 시스템 (2026-08-05 추가)

GDD v2.0을 사용자가 검토한 결과 확정. **깃발의 출발점을 "수도 고정"에서 "내가 소유한 기지 중 선택"으로 바꾼다.** 이것 외에는 v2.0을 건드리지 않는다.

| 결정 | 내용 |
|---|---|
| 기지 배치 | 맵에 **중립 기지 8~12개**를 결정론적으로 배치 (10인/육지 3,900타일 기준). 각 플레이어의 **수도가 최초 기지** |
| 기지의 기능 | **깃발 출발 위치만 제공한다.** 자원 생산·방어 보너스 등 다른 효과 없음 |
| 깃발 슬롯 귀속 | **플레이어 귀속.** v2.0의 슬롯 수 규칙(`TILES_PER_SLOT` 등)을 그대로 유지한다. 기지를 많이 가져도 깃발 수는 늘지 않는다 |
| 기지 점령 | 일반 타일과 동일하게 점령된다. 별도 조건 없음 |
| 회수 목적지 | 출발한 기지. 그 기지를 잃었다면 **남은 내 기지 중 가장 가까운 곳** |
| 기지 상실 시 | 교전 중인 깃발은 **그대로 계속 싸운다.** 소멸하거나 강제 회수되지 않는다 |

**기지의 가치는 오직 행군 지연 단축이다.** v2.0 기준 중반 행군이 약 20초인데 전진 기지를 확보하면 이를 크게 줄일 수 있다. 이는 기동 테크 축 전체보다 강한 효과이므로 8~12개라는 희소성과 맞물려 쟁탈 대상이 된다. 동시에 이것이 지금까지 이 게임에 없던 **"반드시 차지해야 할 지점"**을 지도 위에 만든다.

**아키텍처 주의**: 기지는 위치가 불변이므로 `tile.isBase`(불변 플래그)로 표현하고, 소유권은 `tile.owner`를 그대로 따른다. **새로운 가변 상태를 추가하지 않는다** — "타일은 `owner`만 가변"이라는 v1.0 이래의 원칙이 유지되어야 한다.

**검토 필요**: 전진 기지가 기동 테크 축(`flagSpeedMult`)의 존재 이유를 잠식할 수 있다. 기지를 확보한 플레이어가 기동 축을 살 이유가 없어지면 축 하나가 사장된다.

## GDD v3.0 개정 결정 — 밀도 방어 폐기 + 진척도 모델 (2026-08-11 추가)

GDD v2.1을 사용자가 검토한 결과 확정. **v2.1의 4.7절(본국 자동 방어)을 전면 폐기하고, 전투를 "양방향 진척도 줄다리기"로 바꾼다.** 아래 6개가 사용자 확정 결정이며, game-designer는 이를 전제로 4장·5장을 재작성한다.

### A. 밀도 방어 폐기 (사용자 확정)

| 결정 | 내용 |
|---|---|
| 방어 판정 | **병력 풀은 방어에 일절 관여하지 않는다.** 적 깃발이 들어오면 땅을 뺏긴다 |
| 깃발 출전 페널티 | **없다.** 깃발을 내보내도 방어력이 깎이지 않는다 (`HOME_FLAG_DEF_*` 전부 삭제) |
| `defDensity` | **삭제.** `tileCost`의 밀도항(`ENEMY_BASE + ENEMY_DENSITY_COEF × d`)도 함께 폐기 |

**폐기되는 v1.0 이래의 명제**: "공격에 쓴 병력은 방어력이 아니다", "밀도 2.4배 차이가 붕괴 캐스케이드를 만든다", "큰 쪽은 여럿에게 둘러싸이면 진다(동맹의 근거)". **이 셋의 대체 장치는 game-designer가 새로 설계해 제안하고 사용자 승인을 받는다.**

### B. 방어 수단 = 반격 깃발로 진척도 되돌리기 (사용자 확정)

적 깃발이 내 땅에서 진척도를 채우는 중일 때, 방어자는 **같은 구간으로 자기 깃발을 보내 진척도를 역방향으로 밀어낸다.** 즉 모든 전선이 **양방향 게이지 줄다리기**가 된다.

- 공격과 방어가 **같은 조작(깃발 발령)** 으로 통일된다 — 명령 종류를 늘리지 않는다는 v1.0 이래의 원칙 유지
- game-designer가 반드시 정의할 것: 같은 구간에 공/방 깃발이 동시에 있을 때의 **순증감 해석**, Phase A/B 결정론 구조와의 접합, 게이지가 0으로 되돌아갔을 때의 처리

### C. 진척도는 깃발 단위 상태 (사용자 확정)

타일마다 진척도를 두지 않는다. **서버는 "이 깃발이 지금 밀고 있는 구간의 진척도" 하나만 관리·전송**하고, 클라이언트가 그 값으로 전선을 그라데이션 렌더링한다.

- **"타일은 `owner`만 가변"이라는 v1.0 이래의 원칙이 유지된다** (v2.1 기지 조항과 동일한 이유)
- 스냅샷 대역폭 증가는 깃발당 수 바이트로 제한된다
- 시각 표현: 공격이 들어오는 방향에서 그라데이션이 차오르며, 얼마나 진척됐는지가 화면에서 읽혀야 한다

### D. 기지 체력 바 (사용자 확정)

| 결정 | 내용 |
|---|---|
| 기지는 체력을 갖는다 | 공격받으면 **공격자 색으로 점점 칠해진다** (체력 바 + 타일 채색) |
| 회복 | **공격이 없으면 체력이 점차 찬다** |
| 체력 0 | **소유권이 공격자에게 이전되고, 새 주인 기준 체력 50에서 시작한다** (만피 아님) |

- 즉 기지는 일반 타일과 달리 "진척도 게이지"가 아니라 **지속 상태인 체력**을 갖는다. 이것이 v2.1까지 유지된 "타일은 `owner`만 가변" 원칙의 **유일한 예외**이며, 기지는 맵 전체에 최대 24개이므로 대역폭·결정론 비용이 상한선 안에 묶인다
- game-designer가 정의할 것: 최대 체력, 회복률, 깃발 병력이 체력을 깎는 환산식, 체력 50 시작이 연속 함락에 주는 영향

### E. 병력 풀 = 순수 발령 자원 + 상한 유지 (사용자 확정)

병력은 **오직 깃발을 채우는 자원**이다. `troopCap`(타일당 12)과 로지스틱 감쇠는 **유지한다** — 상한이 차면 재생이 멈추므로 "쟁여두면 손해"가 되어 계속 내보내는 압력이 유지된다.

- 눈덩이 억제는 기존 `√타일` 재생 감쇠 + 중립 비용 `√타일` 상승이 계속 담당한다
- `troopCap`의 의미가 "방어 밀도 상한"에서 **"동시 투사 가능 총량 상한"** 으로 바뀐다. game-designer는 이 재해석으로 5장 페이싱이 여전히 30~60분에 수렴하는지 재검산한다

### F. 재설계가 필요한 파급 항목 (game-designer 필수 처리)

1. **창병의 정체성 붕괴** — v2.1 창병은 "느리게 가면서 본토를 지킨다"였는데 본국 방어 기여가 사라져 **존재 이유가 없어진다.** 반드시 재정의할 것 (예: 진척도 되돌리기/버티기에 강한 병종)
2. **`tileCost`에서 밀도항 제거 후 남는 것** — 지형·응집·병종·테크뿐. 비용 분산이 충분한지, 붕괴 캐스케이드를 대체할 장치가 필요한지 검토
3. **동맹의 근거 재정립** — "둘러싸이면 진다"가 사라진 자리에 무엇이 동맹을 만드는가
4. **`DEFENDER_LOSS_RATIO` / `LOSER_TO_DEFENDER_RATIO`** — 방어자 병력 손실 개념을 유지할지 폐기할지
5. **5장 세션 페이싱 전면 재검산** — 방어가 사라지면 확장이 빨라져 세션이 짧아진다. 30~60분 수렴을 다시 증명할 것
6. **7장 프로토콜** — 깃발 진척도 필드 + 기지 체력 필드 추가, 대역폭 재검산
7. **8장 봇 AI** — 방어 개념 변경 반영
8. **미결정 사항 #1(`FRONT_RADIUS=6`)과 #8(`ENDGAME_RUSH_TICK=37분`)** — 새 모델 기준으로 재검토

## GDD v3.0 「미결정 [A]」 5건 사용자 확정 (2026-08-12 추가)

### A-1 상세 — 골드 주둔 유지비

- 소모 자원을 **병력 → 골드**로 교체한다. `FLAG_GARRISON_UPKEEP_BP`(병력 basis point)는 폐기하고 골드 기준 상수를 새로 설계한다.
- 튜닝 목표: 방어 깃발을 여러 개 세운 상태에서 **골드 순증가량이 눈에 띄게 둔해지되 순감소(적자)로는 떨어지지 않는다.** 3.3절 골드 수입 모델과 함께 검산할 것.
- 파급: 골드는 테크 구매 원천이므로 **3.3절(골드) + 3.4절(테크) + 5장 테크 페이싱**을 다시 검산해야 한다. "무한 웅크리기 차단"이라는 원래 목적(4.4절)이 골드 압력만으로도 성립하는지 증명할 것.
- 부수 효과 판단: 병력이 안 깎이므로 방어 깃발은 회수 시 병력을 온전히 돌려주지만, 대신 **테크 진행이 늦어지는 것**이 방어의 기회비용이 된다. 이 해석이 A항(병력 풀은 방어에 일절 관여하지 않는다)과 더 잘 맞는다.

### A-5 상세 — 자세 개념 제거

- 서버 내부에서 앵커 소유자로 동작을 분기하는 것은 그대로 두되, **`posture` / `ATTACK` / `DEFEND`를 UI·튜토리얼·프로토콜 표면의 1급 개념으로 노출하지 않는다.** GDD 문면도 "자세를 고른다"가 아니라 "어디로 보내느냐에 따라 결과가 다르다"로 기술한다.
- 클라이언트는 모드 표시나 토글을 두지 않는다. 커서/프리뷰가 **결과**(게이지가 어느 방향으로 움직일지)만 보여준다.
- 내 땅으로 보낸 깃발은 **이동(재배치)도 겸한다** — 방어 전용 명령이 아니다. 이 이중 용도를 4장에 명시할 것.

## GDD v4.0 개정 결정 — 해안/수상 이동 (2026-08-12 추가)

v1.0 이래 물은 **순수한 벽**(통행 불가·점령 불가)이었다. 이를 폐기하고 수상 이동을 도입한다.

| # | 사용자 확정 |
|---|---|
| 1 | **물을 얕은 물 / 깊은 물로 나눈다. 얕은 물로만 통행 가능**, 깊은 물은 종전대로 벽 |
| 2 | **물은 주인 없는 통로다.** 점령 불가 — `owner`를 갖지 않는다 |
| 3 | **물 위에서 싸울 수 있다** |
| 4 | **제약 없음** (일단). 병종·테크·기지 조건을 붙이지 않는다 |

### 폐기되는 전제

- 2.2절 「물 Water — 통행/점령 불가」 한 줄 → 얕은 물은 통행 가능으로 갈라진다
- 4.3절 발령 거절 사유 `WATER` → 얕은 물 앵커는 허용 여부를 재정의해야 한다
- 4.1절 `front()` / `guard()` 후보에서 물 제외 → 재정의
- `BASE_MIN_WATER_DIST = 2`의 근거 소멸 (물이 벽이 아니게 되므로)
- 2.4절 맵 생성이 "물 = 벽" 전제 위에 있다 (v2.1 문서 참조 상태)

### 설계자가 반드시 처리할 것

1. **지형 종류가 6 → 7로 늘어난다.** `TERRAIN` enum, 지형 표, 맵 생성 비율, `TERRAIN_COST_MULT` / `TERRAIN_MOVE_PERMILLE` 전부 확장
2. **토폴로지 추상화 안에서 처리할 것.** 얕은 물 통행 여부는 `neighbors(tileId)` 내부 판단으로 두어 게임 로직이 안 바뀌게 한다 (구현 제약 준수)
3. **5장 세션 페이싱 재검산** — 바닷길이 생기면 이동 거리가 짧아진다. 표준 종료 39.2분 / 실질 하한 34.5분 / 하드 타임아웃 42분 유지를 다시 증명할 것
4. **8장 봇 AI** — 앵커 선택·경로가 해상을 고려해야 한다
5. **6장 점유율** — 물은 점령 불가이므로 `totalLandTiles` 분모는 그대로여야 한다. 얕은 물이 늘어 육지가 줄면 임계 45%의 실질 난이도가 바뀌는지 확인

### 5. 깃발 대 깃발 직접 전투 (2026-08-12 사용자 확정 — 물 한정이 아님)

> **사용자 원문**: "깃발끼리 전투하여 병력을 깎는다고, 육지에서의 깃발과 깃발이 만나면 동일하게 진행할거야."

- **적 깃발끼리 만나면 서로의 병력을 깎는다.** 물 위뿐 아니라 **육지에서도 동일하게** 적용한다.
- 이것은 해안 기능의 부속이 아니라 **전투 모델 자체의 변경**이다. v3.1까지 깃발은 서로를 통과했고, 모든 전투가 "타일 게이지를 밀고/되돌리는" 것으로만 이루어졌다.
- 따라서 이 개정은 **v4.0**이며, 승인된 v3.1의 4장·5장 일부를 다시 연다.

#### D-1 ~ D-3 사용자 확정 (2026-10-05)

| # | 확정 |
|---|---|
| **D-1** | **직접 전투 중에는 타일 게이지가 차지 않는다** (정지) |
| **D-2** | **인접하면 전투 개시** (`FLAG_ENGAGE_RANGE = 1`) |
| **D-3** | **진 깃발은 자동 귀환. 귀환 중에는 조작 불가** |

- D-1 리스크 재평가: 전투는 반드시 한쪽 패배(→ 자동 귀환)로 끝나므로 "붙여두기"는 영구 동결이 아니라 **병력 대결**로 귀결된다. 다만 게이지 반격(4.7)과 직접 격파 중 어느 쪽이 방어에 효율적인지는 설계자가 4.7절에서 재검산해야 한다.
- D-2 귀결: 회피가 사실상 불가능하므로 적 깃발 인접 경로의 모든 행군이 전투가 된다. 봇 AI 경로 판단(8장)에 반영.
- D-3 보충 (사용자 원문: "전투동안 서로 병력을 소모하고 다 떨어지면 깃발만 패주하게 되는거야"): 전투는 **한쪽 병력이 0이 될 때까지** 서로 소모. 패주하는 깃발은 **병력 0** → 환급할 병력이 없다. 패주 깃발은 귀환 완료까지 슬롯을 점유하며 조작 불가.

## 구현 제약 (백엔드/프론트엔드 대상 — 2026-08-04 추가)

### 토폴로지 추상화 필수

맵 격자는 **사각으로 구현하되, 육각으로 교체 가능하도록 추상화 레이어를 둔다.** (사용자 확정)

- `neighbors(tileId) -> tileId[]`, `distance(a, b) -> number`, `tileCount()` 정도의 최소 인터페이스를 정의하고, 전투 알고리즘·맵 생성·스폰 배치·봇 AI는 **이 인터페이스만 호출**한다.
- `row * width + col`, `manhattan(a, b)`, `id ± 1 / id ± width` 같은 사각 격자 전제를 게임 로직 안에 직접 박아넣지 않는다. 그런 식은 사각 구현체 파일 안에만 존재해야 한다.
- 클라이언트도 마찬가지로 `pixelToTileId`와 타일 그리기를 렌더 모듈 한 곳에 격리한다.
- 목표: 육각 전환이 "구현체 교체 + 밸런스 상수 재조정"으로 끝나야 하며, 게임 로직 파일들을 헤집지 않아야 한다.

> **왜**: 육각 전환은 프로토콜 shape을 바꾸지 않는다(서버는 여전히 `{id, owner}` 배열을 보냄). 즉 경계면은 안전하고, 순수하게 서버 내부 + 렌더링 문제다. 지금 추상화 한 겹을 넣어두면 나중 전환 비용이 크게 줄어든다.

**곡선형(불규칙 폴리곤)은 범위 밖이다.** 곡선형은 "타일 1개 = 가치 1단위"라는 경제 모델 전제 자체를 깨므로 추상화로 커버되지 않으며, 필요해지면 GDD부터 면적 가중으로 재설계해야 한다. 현재 계획에 없다.

## 설계 시 특별히 주의할 점

1. **동맹 시스템과 승리조건의 상호작용** — 사용자가 동맹을 원했으므로, "막판에 2인이 동맹인 채로 점유율 임계값에 도달하면 어떻게 판정하는가", "동맹 파기 직후 즉시 공격 가능한가(백스탭 쿨다운)"를 반드시 규칙으로 정의한다. 이걸 비워두면 서버 구현 단계에서 임의 결정되어 GDD와 어긋난다.
2. **테크 4축 × 세션 3~5회 구매** — 축이 4개인데 세션 중 3~5개만 찍는다면, 플레이어는 "어느 축에 집중할지" 선택하게 된다. 이는 의도된 트레이드오프이므로 각 축의 1단계 효과가 서로 비교 가능한 크기여야 한다.
3. **세션 페이싱 계산 근거를 반드시 남길 것** — 맵 타일 수 / 10인 기준 / 확장 속도로 "왜 목표 대역(25~32분, 표준 30분)에 수렴하는지" 계산을 GDD에 명시한다.
4. **전체 공개 시야** — 서버 브로드캐스트는 단일 스냅샷이면 충분하다. 프로토콜을 플레이어별로 분기시키지 않는다.
